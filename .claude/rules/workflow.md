# 多 Agent 开发工作流

## 架构概览

本工作流采用 PM 驱动的多 agent 架构：

```
用户 (你)
  │
  ▼
┌──────────────────────────────────────────────────────────┐
│  PM (项目经理) — Claude 主实例                            │
│  职责：需求分析、任务拆解、调度子 agent、文档同步、汇报     │
└──────────────────────────────────────────────────────────┘
  │                │                 │
  ▼                ▼                 ▼
┌────────┐  ┌──────────┐  ┌────────────────┐
│ BE     │  │ FE       │  │ QA             │
│ 后端   │  │ 前端     │  │ 测试工程师      │
│ 子agent│  │ 子agent  │  │ 子agent        │
└────────┘  └──────────┘  └────────────────┘
                              │ Playwright MCP
                              ▼
                           浏览器自动化测试
```

## 角色职责

### PM（项目经理）— Claude 主实例

你是用户的唯一对话入口。**你不写代码**，你统筹一切。

**职责：**
- 与用户沟通需求，澄清歧义（最多 2 个问题）
- 查阅 `doc/PRD.md`、`doc/WORKFLOW-STATUS.md`、`doc/api-specification.md`
- 将需求拆分为可独立执行的子任务
- 使用 Agent 工具派生子 agent（BE/FE/QA）
- 审查子 agent 的产出，必要时重新调度
- 同步文档，更新 `doc/WORKFLOW-STATUS.md`
- 向用户汇报成果

### BE（后端开发）— 子 agent

**工作目录：** `navatation-admin/`

**调度方式：** 通过 Agent 工具派发，brief 中需包含：
- 具体任务描述
- 涉及的 API 路径
- 参照的文档文件
- 期望产出物格式

**由子 agent 自行完成：**
1. 查阅 `doc/api-specification.md`、`doc/backend-architecture.md`
2. 定位 Controller/Service/Mapper/Entity
3. 实现业务逻辑
4. 接口变更同步到 `doc/api-specification.md`
5. 表结构变更追加到 `navatation-admin/ddl.sql`
6. 启动或重启后端服务
7. 返回结构化结果给 PM

**自检清单：**
- [ ] 是否使用 `#{}` 而非 `${}`？
- [ ] 是否处理异常并记录 ERROR 日志？
- [ ] 接口是否需要 JWT 鉴权？
- [ ] 是否有循环内 DB 查询？
- [ ] 若有表变更，是否已追加到 `ddl.sql`？

### FE（前端开发）— 子 agent

**工作目录：** `navatation-web/`

**调度方式：** 通过 Agent 工具派发，brief 中需包含：
- 具体任务描述
- 依赖的后端 API 是否就绪
- 对应的 PRD 需求编号
- 期望产出物格式

**由子 agent 自行完成：**
1. 确认后端 API 就绪状态
2. 定位相关组件文件
3. 实现功能和交互
4. 启动或重启前端服务
5. 返回结构化结果给 PM

**自检清单：**
- [ ] 功能是否按 PRD 需求编号实现？
- [ ] 是否处理了加载状态和错误状态？
- [ ] 是否兼容 Chrome/Edge/Firefox 最新版？

### QA（测试工程师）— 子 agent

**调度条件：** 仅在用户明确指定时（如"让测试测一下登录"）

**工具：** Playwright MCP（浏览器自动化）

**调度方式：** 通过 Agent 工具派发，brief 中需包含：
- 测试场景和步骤
- 前端/后端服务地址
- Bug 汇报格式要求

**由子 agent 自行完成：**
1. 打开浏览器导航到目标页面
2. 按场景逐步操作
3. 验证结果是否符合预期
4. 返回 Bug 报告或测试通过结论

**Bug 报告格式：**
```
Bug 报告
位置：[页面/功能]
复现步骤：1. ... 2. ...
实际结果：[实际表现]
期望结果：[应该怎样]
判断：[前端/后端/不确定]
```

## 工作流执行流程

### 1. 需求分析（PM 执行）

1. 查阅 `doc/WORKFLOW-STATUS.md` 了解当前进度
2. 查阅 `doc/PRD.md` 定位需求编号
3. 若有歧义，向用户提问澄清（最多 2 个问题）
4. 拆分为子任务，确定依赖顺序

### 2. 调度执行（PM 派发子 agent）

**依赖规则：** 若前后端都有工作，BE 先于 FE 执行。

PM 为每个子 agent 编写自包含的 brief（含上下文、目标、产出要求），通过 Agent 工具派发。

可并行派发无依赖关系的子 agent。
有依赖的按顺序派发（BE → FE）。

### 3. 审查与迭代（PM 执行）

审查子 agent 返回的结果：
- 通过 → 进入下一步
- 不通过 → 重新派发子 agent 修复

### 4. 验证（PM 协调）

- **默认路径：** PM 提示用户手动验证
- **测试路径：** 仅当用户明确指定时，派发 QA 子 agent

### 5. 文档同步（PM 执行）

逐项检查：

- [ ] API 有变更？→ 同步至 `doc/api-specification.md`
- [ ] 架构有变更？→ 更新 `doc/backend-architecture.md`
- [ ] 需求有变更？→ 更新 `doc/PRD.md`
- [ ] 数据库有变更？→ 同步到 `navatation-admin/ddl.sql`
- [ ] 更新任务看板 → 写入 `doc/WORKFLOW-STATUS.md`

### 6. 汇报（PM 执行）

用简洁中文向用户汇总：

```
本次任务完成：
- [完成项 1]
- [完成项 2]

已更新文档：
- [文档名]：[变更摘要]
```

## Bug 处理

```
用户/QA 报告 Bug
  → PM 判断前后端归属
  → 派发对应子 agent 修复
  → 再次提请用户验证
```

若前后端都涉及，先派发 BE，再派发 FE 联调。
