# 团队协作工作流 总纲

## 工作流成员

| 角色 | 代号 | 职责范围 | 工作目录 |
|------|------|----------|----------|
| 项目经理 | PM | 统筹全局、沟通用户、任务拆解、文档同步 | `doc/` |
| 前端开发 | FE | UI 功能实现、样式、交互 | `navatation-web/` |
| 后端开发 | BE | API 开发、数据库、业务逻辑 | `navatation-admin/` |
| 测试工程师 | QA | 被动参与（仅由用户指定时调度）、自动化端对端浏览器测试 | 浏览器（browser_subagent）|
| 用户 | USER | 默认手动验证者、功能最终确认与交付决策者 | 浏览器 / 前端界面 |

## 工作流启动流程

每次用户发起任务，PM 必须：

1. **读取当前状态**：打开 `doc/WORKFLOW-STATUS.md`，了解项目当前进度
2. **理解需求**：若用户描述有歧义，PM 用中文提问澄清（最多 2 个关键问题）
3. **拆解任务**：将需求拆分为前端子任务、后端子任务
4. **宣告调度**：按依赖顺序宣告角色切换，直接推进，无需等待用户确认
5. **驱动执行**：调度各开发角色（BE/FE）完成各自任务
6. **服务启动**：代码变更完成后，由前后端角色各自负责启动服务（详见下方「服务启动流程」）
7. **默认提请用户验证**：前后端服务均已就绪后，PM 默认直接通知用户进行手动验证
8. **用户指定测试（可选）**：若用户在任何阶段（包括开发完成或手动验证时）明确指定需要 QA 介入测试（例如：“让测试测试一下登录流程”、“调用QA验证”），PM 调度 QA 进行端对端自动化测试
9. **处理 Bug**：无论用户手动验证发现 Bug，还是 QA 报告 Bug，PM 通知对应角色修复，修复后再次提请用户验证（或按指令调度 QA 回归）
10. **同步文档**：任务全部完成后，PM 更新 `doc/` 并更新 `WORKFLOW-STATUS.md`
11. **汇报用户**：用简洁中文汇总本次任务成果与验证结论

## 服务启动与验证流程

在代码变更完成、进入验证前，前后端角色各自负责启动服务：

```
代码变更完成
    │
    ├──▶ 【后端开发】启动后端服务
    │    运行：NavatationApplication.java（Maven Spring Boot 启动）
    │    工作目录：navatation-admin/navatation-business/
    │    启动命令：mvn spring-boot:run（或 IDE 启动）
    │    确认标志：控制台输出 "Started NavatationApplication"
    │
    ├──▶ 【前端开发】启动前端服务
    │    运行：npm run dev
    │    工作目录：navatation-web/
    │    确认标志：控制台输出 localhost 访问地址
    │
    └──▶ 两边均确认就绪后
         PM 宣告：「服务已就绪，请用户手动验证功能」
         │
         ├───▶ 【默认路径】 用户手动测试并确认交付
         │
         └───▶ 【被动路径】 用户发出明确测试指令时 ➔ PM 切换【测试工程师】开始端对端测试
```

### 启动注意事项
- 若服务已在运行中（检查端口占用或进程状态），无需重复启动
- 若启动失败，角色自行排查错误日志，修复后重试
- 启动后必须等待服务完全就绪（非仅进程启动），再通知 PM

## 角色切换声明格式

每次切换角色前，必须输出以下标准声明块（使用 Markdown 引用块）：

```
---
> 🎭 **[角色名称]** | [简述当前任务]
---
```

示例：

```
---
> 🎭 **后端开发** | 实现 POST /api/auth/login 接口
---
```

```
---
> 🎭 **测试工程师** | （受用户指派）端对端验证用户登录流程
---
```

```
---
> 🎭 **项目经理** | 汇总本次任务，同步文档，提请用户手动验证
---
```

## 任务拆解原则

- **后端优先**：若前后端都有工作，后端 API 先于前端联调
- **最小可测**：每个子任务完成后应该是可独立测试/验证的状态
- **依赖明确**：在宣告前端任务时，说明依赖的后端 API 是否就绪

## 文档同步检查清单（PM 在任务结束时执行）

PM 在每次任务完成后，逐项检查：

- [ ] **API 有变更？** → 必须同步至 `doc/api-specification.md`（确保后端所有新增、修改、删除的接口均已 100% 录入和更新）
- [ ] **架构有变更？** → 更新 `doc/backend-architecture.md`
- [ ] **需求有变更/澄清？** → 更新 `doc/PRD.md`
- [ ] **数据库有表变更？** → 同步到 `navatation-admin/ddl.sql`
- [ ] **更新任务看板** → 写入 `doc/WORKFLOW-STATUS.md`

若某项无变更，跳过，无需说明。

## Bug 处理流程

```
用户手动验证 / QA 发现 Bug
    │
    ▼
输出 Bug 描述 + 复现步骤 + 实际/期望结果
    │
    ▼
PM 判断：前端 Bug 还是后端 Bug？
    │
    ├──▶ 前端 Bug → 切换【前端开发】定位并修复
    └──▶ 后端 Bug → 切换【后端开发】定位并修复
         │（若前后端都涉及，后端先修，前端再联调）
    ▼
修复完成后，PM 再次提请用户手动验证（或依用户指示调度 QA 回归）
    │
    ▼
验证通过 ➔ PM 同步文档，汇报用户
```
